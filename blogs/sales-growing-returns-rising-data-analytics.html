Sales Are Growing, but Returns Are Rising Too: How Data Analysts Find the Real Problem

A retailer celebrates a 20% increase in sales, but the returns team is also processing more products than usual. Revenue reports look positive, yet returned orders can reduce net sales, increase handling costs, and create extra work for customer support and operations. The important question is not simply whether returns increased; it is whether returns are growing faster than sales, where the change is concentrated, and what the data can reliably tell us.

In a practical analytics project, analysts can connect sales and returns records, validate the measures, compare product and regional patterns, and present evidence that helps the business decide what to investigate next.

Start with a clear business question

Define the question before opening a spreadsheet: Which products, categories, channels, or regions have a rising return rate, and what operational factors should the team investigate? Agree on the measurement window and define a return consistently. For example, decide whether a return rate is calculated by units, orders, or sales value. These measures answer different questions and should not be mixed.

Important: a rise in the number of returns does not automatically mean product quality has worsened. If sales volume grew, returns may also rise while the return rate stays stable or even falls.

Step 1: Prepare and validate the data in Excel

Begin with sales order lines, product details, and return transactions. Keep an untouched copy of each source and record the extract date. Useful checks include:

  • Find missing order IDs, SKU values, quantities, dates, and return reasons.
  • Check duplicate records, while confirming whether repeated order IDs represent separate line items rather than errors.
  • Standardize product identifiers, category names, dates, and return-status labels.
  • Confirm that cancelled orders and pending returns are treated consistently.
  • Check whether returns can occur in a different reporting period from the original sale.
  • Reconcile row counts and sales totals with the source system before analysing trends.

Excel filters, PivotTables, conditional formatting, COUNTIF, and XLOOKUP can help identify suspicious records and compare totals by product or month. Do not silently delete unusual rows; investigate and document any corrections.

Step 2: Calculate comparable return metrics

Use a measure that matches the business question. A simple unit return rate can be calculated as returned units divided by units sold for a comparable cohort and period. An order return rate instead uses returned orders divided by eligible orders. A value-based rate compares the value of returned goods with the relevant sales value, using a clearly stated accounting rule.

For example, suppose a category sold 1,000 units and 80 units were returned in one period. Its unit return rate is 8%. In the next period, sales rise to 1,500 units and returns rise to 105 units. Returns increased in count, but the unit return rate is 7%. That pattern alone does not support the conclusion that the category is becoming less reliable.

For accurate comparisons, align the numerator and denominator. Returns may lag the original sale, so recent sales cohorts can appear to have fewer returns simply because customers have not had enough time to return them. State this limitation clearly.

Step 3: Use SQL to find where return rates are changing

SQL can aggregate sales and return lines by product category. The following is an illustrative query: adapt table names, date logic, status filters, and return matching rules to the available database. It assumes the sales and return tables store unit quantities and that returned units can be grouped by SKU.

WITH sales_by_sku AS (
  SELECT
    sku,
    SUM(quantity) AS units_sold
  FROM sales_order_lines
  WHERE order_status = 'completed'
    AND order_date >= DATE '2026-09-01'
    AND order_date <  DATE '2026-10-01'
  GROUP BY sku
),
returns_by_sku AS (
  SELECT
    sku,
    SUM(return_quantity) AS units_returned
  FROM return_lines
  WHERE return_status = 'accepted'
    AND return_date >= DATE '2026-09-01'
    AND return_date <  DATE '2026-11-01'
  GROUP BY sku
)
SELECT
  s.sku,
  s.units_sold,
  COALESCE(r.units_returned, 0) AS units_returned,
  1.0 * COALESCE(r.units_returned, 0)
    / NULLIF(s.units_sold, 0) AS return_ratio
FROM sales_by_sku s
LEFT JOIN returns_by_sku r
  ON s.sku = r.sku
ORDER BY return_ratio DESC;

This example is a starting point, not a universal accounting formula. It uses different sales and return windows to illustrate that return timing needs deliberate handling; for a production metric, link returns to their original sale where possible and compare mature cohorts. If returns can exceed sales in a short window because of earlier purchases, do not interpret the resulting ratio as a same-period cohort return rate.

After validating the metric, join the product dimension to compare categories and product attributes. Add channel or region only when the data supports those comparisons. Check join cardinality to avoid multiplying sales or returns through duplicate product or order keys.

Step 4: Treat possible causes as hypotheses

Once a product or category stands out, develop explanations to test rather than jumping to a conclusion. A higher return rate could be associated with several factors:

Pattern in the dataHypothesis to testUseful follow-up
Returns cluster around certain sizes or variantsFit, sizing, or variant information may be unclearReview variant-level rates and customer feedback
Return reasons mention mismatch with listingProduct descriptions or images may set incorrect expectationsAudit listing details and compare reason codes
Returns are concentrated in a delivery regionShipping damage or delivery experience may be a factorCompare carrier, packaging, delivery, and damage records
A single batch has an unusual rateA supplier or quality-control issue may existInspect batch records and quality checks
One channel shows a sudden changePolicy, customer mix, or recording practices may have changedCheck policy dates, channel definitions, and data capture

Return reason fields can be incomplete or inconsistently entered. Treat them as useful signals, not perfect evidence. Compare multiple sources, check sample sizes, and document what would confirm or disprove each hypothesis.

Step 5: Build a Power BI dashboard for decisions

A decision-focused dashboard should help a team identify the next investigation, not just display a wall of charts. Consider these visuals:

  • Summary cards: units sold, units returned, return rate, and net sales, with definitions and reporting period visible.
  • Trend chart: sales and return rates over time, using comparable cohorts and noting incomplete return windows.
  • Category and SKU table: return rate, units sold, units returned, and sample size.
  • Reason breakdown: accepted return reasons by category, with unknown or blank reasons shown separately.
  • Region and channel comparison: use filters that allow meaningful comparisons without hiding small sample sizes.
  • Drill-through details: let authorised users inspect order and return records behind a result.

Validate dashboard totals against source reports, check filter behaviour, and show the last successful refresh time. A return-rate card without its definition, denominator, or time window can mislead even when the calculation itself is technically correct.

Step 6: Recommend actions and measure the result

Prioritise recommendations by evidence, customer impact, and the effort needed to test them. Depending on the findings, a business might improve product information, inspect a supplier batch, review packaging, clarify size guidance, or investigate a delivery partner. These are possible actions only when supported by the analysis.

Agree on a baseline and a follow-up period before making changes. Track the chosen return-rate measure alongside sales volume, customer complaints, net sales, and operational costs. Where possible, compare similar products or groups and account for seasonality or policy changes. Avoid claiming that a change caused an improvement if the data only shows that both happened at the same time.

Turn the investigation into a portfolio project

A portfolio-ready project should make the reasoning easy to review. Use public or synthetic data rather than confidential customer or employer records, and include:

  1. A concise business problem and written metric definitions.
  2. An Excel quality-check workbook or documented validation checklist.
  3. SQL queries with comments explaining joins, filters, and return-window assumptions.
  4. A Power BI dashboard with clear labels, filters, and data-refresh information.
  5. Three evidence-backed findings, each paired with a limitation or alternative explanation.
  6. A prioritised action plan and a proposed way to measure whether the action works.

The project is stronger when it explains uncertainty. Show the difference between a descriptive finding (“this category has a higher observed return rate”) and a causal claim (“this product feature caused returns”). The second claim requires stronger evidence than a dashboard comparison alone.

Building practical analytics skills

This kind of investigation connects data cleaning, spreadsheet analysis, SQL aggregation, dashboard design, and business communication. When exploring Analytics Training in India, look for learning that includes realistic datasets, hands-on practice, validation of metrics, and projects where you must explain assumptions as well as results.

Tools are important, but the real value comes from asking a precise question, checking whether the data can answer it, and recommending the next step without overstating what the evidence proves.
