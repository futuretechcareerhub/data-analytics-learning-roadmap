When Numbers Lie: A Practical Guide to Data Quality for Analysts

How to catch bad data before it becomes a bad business decision.

Published: October 1, 2026

A dashboard can look polished, the SQL can be correct, and the charts can update automatically — yet the final insight can still be wrong.

The problem is often not the analysis itself. It is the quality of the data underneath it.

For analysts, data quality is not just a technical cleanup task. It is part of analytical thinking. Before calculating a KPI, building a dashboard or presenting a recommendation, you need confidence that the numbers actually represent the business reality you are trying to measure.

What Does Data Quality Mean in Analytics?

Data quality describes how suitable a dataset is for the purpose for which it will be used. A dataset can be perfectly formatted and still be unsuitable if important records are missing, definitions are inconsistent or values are outdated.

For practical analytics work, six dimensions are especially useful:

DimensionQuestion to ask
AccuracyDo the values represent reality?
CompletenessAre important records or fields missing?
ConsistencyAre the same concepts represented in the same way?
ValidityDo values follow the expected format and rules?
TimelinessIs the data current enough for this decision?
UniquenessAre duplicate records distorting the results?

Why Good-Looking Data Can Still Be Wrong

One of the easiest mistakes is assuming that a clean-looking spreadsheet is trustworthy. Consider a sales report where the revenue column contains no blanks. That does not prove the revenue values are correct.

Possible problems could include duplicate orders, cancelled transactions included as sales, refunds not deducted, different currencies mixed together, or revenue being calculated from inconsistent definitions.

This is why a strong analyst asks what each field means and how the data was generated before using it.

Start With the Business Definition

Before checking rows and columns, define what you are actually trying to measure.

Suppose a company asks for its “monthly active customers.” That phrase sounds straightforward, but several definitions are possible:

  • Customers who logged in during the month
  • Customers who made a purchase
  • Customers who placed a paid order
  • Customers who used a specific product feature

All four can produce different numbers. The first data-quality question is therefore not “Are there null values?” It is “What exactly does this metric mean?”

A Practical Data Quality Workflow

  1. Understand the dataset: identify the grain, important fields, sources and update frequency.
  2. Check structure: inspect data types, column names, date fields and expected formats.
  3. Measure completeness: identify missing values in important fields.
  4. Check uniqueness: look for duplicate IDs, orders, customers or events.
  5. Validate ranges: investigate impossible or suspicious values.
  6. Check consistency: compare categories, naming conventions and units.
  7. Check relationships: verify joins and record counts between related tables.
  8. Document assumptions: record decisions made during cleaning and metric calculation.

Useful Checks in Excel

Excel remains useful for quick data-quality inspection, especially when analysts receive smaller operational datasets.

  • Filter and sort suspicious values
  • Use COUNTIF and COUNTIFS to identify duplicates or unexpected categories
  • Use conditional formatting for unusual values
  • Check blanks in critical columns
  • Compare totals against known business figures
  • Inspect date ranges and inconsistent formats

The goal is not to replace a full analytics workflow with Excel. It is to quickly identify obvious problems and understand the dataset.

SQL Checks Every Analyst Should Know

SQL is particularly useful when data-quality checks need to be repeatable.

Find duplicates

A simple GROUP BY with HAVING can reveal IDs that occur more than once.

Check missing values

Use NULL checks on fields that should normally be populated, such as order IDs, transaction dates or customer IDs.

Check suspicious ranges

Look for negative quantities, impossible dates, unusually large values or values outside known business limits.

Validate joins

When joining tables, compare row counts and key coverage before assuming the resulting dataset is correct. An unexpected many-to-many join can multiply records and inflate totals.

Power BI and Dashboard Data Quality

Data quality problems become especially dangerous when they reach dashboards because a dashboard can make questionable numbers look authoritative.

Before publishing a Power BI report, check:

  • Source refresh status
  • Relationships between tables
  • Duplicate keys
  • Measure definitions
  • Filters and slicers
  • Date/calendar logic
  • Totals against a trusted source

A useful practice is to create a small validation page or hidden QA section containing record counts, totals and refresh information. This makes future checks easier.

Data Validation vs Data Cleaning

These two ideas are related but not identical.

Data cleaningData validation
Fixes or transforms problematic dataChecks whether data meets expected rules
May standardize categoriesMay flag unexpected categories
Can remove duplicatesCan detect duplicates
Can fill or handle missing valuesCan measure completeness

A mature workflow does both. Cleaning without validation can hide problems; validation without an agreed process may simply produce a list of issues without resolving them.

How Data Quality Changes the Final Insight

Imagine a company reports that average order value increased by 18%. Before celebrating the result, an analyst should ask:

  • Did the number of orders change?
  • Were refunds included?
  • Did the customer mix change?
  • Were duplicate transactions introduced?
  • Did the date filter change?
  • Was the same revenue definition used last month?

Good analytics is not just calculating the number. It is understanding whether the number deserves to be trusted.

What This Means for Someone Learning Data Analytics

Data quality is a valuable skill because it connects technical tools with business reasoning. A learner who knows Excel, SQL and Power BI but cannot question a suspicious number is still missing an important part of the analyst role.

Common Data Quality Mistakes

Deleting every row with a missing value

Missingness has meaning. Removing rows without understanding why data is missing can introduce bias.

Removing every outlier

An unusual value may be an error, but it may also represent a real high-value customer or exceptional business event.

Trusting a dashboard because it looks professional

Visual polish does not validate the underlying data.

Fixing data without documenting the change

Future analysts need to know what was changed, why it was changed and which assumptions were made.

Checking quality only once

Data quality can change after every source refresh. Important checks should become repeatable.

Frequently Asked Questions

Why is data quality important in data analytics?

Poor-quality data can produce misleading KPIs, incorrect trends and weak business recommendations even when the analysis itself is technically correct.

What should a data analyst check first?

Start with the business definition, dataset grain, important fields, date range, duplicates, missing values and expected relationships between tables.

Can Excel be used for data-quality checks?

Yes. Excel is useful for quick inspection, duplicate checks, missing-value checks and basic validation of smaller datasets.

Is SQL useful for data validation?

Yes. SQL makes many checks repeatable and works well for duplicates, missing values, ranges, categories, joins and reconciliation.

Does data quality matter for Power BI?

Yes. A dashboard can make incorrect numbers appear authoritative, so source data, relationships, measures and refreshes should be validated.

Trust the Data Before Trusting the Dashboard

The strongest analysts do not simply report numbers. They understand where those numbers came from, test whether they make sense and communicate the assumptions behind them.
