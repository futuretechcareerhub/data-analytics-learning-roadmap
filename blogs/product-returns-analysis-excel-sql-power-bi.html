Why Are Customers Returning Their Orders? A Data Analytics Investigation of Product Returns

A step-by-step investigation of return patterns—from messy order records to useful business decisions—with Excel, SQL and Power BI.

Published: November 17, 2026 · Reading time: 8–10 minutes

Product returns can quietly reduce a retailer’s margins. A business may report healthy order volumes while refunds, reverse-logistics costs and replacement shipments eat into the value of those sales. The important question is not simply how many orders came back, but which products are returned, why customers return them, and what patterns can the business act on?

In this practical case study, imagine an online retailer that wants to understand a rise in product returns. We will follow an analyst’s workflow: define useful measures, prepare the data in Excel, investigate return patterns with SQL, and present the findings in Power BI.

Business question: Which products and categories have unusually high return rates, what reasons are most common, and what operational changes could reduce avoidable returns?

1. Understand the data before calculating anything

Start with two related datasets: an orders table and a returns table. The orders table records completed purchases; the returns table records returned quantities, dates and customer-reported reasons.

Order ID, Order Date, Product IDReturn ID, Order ID, Product ID
Category, Quantity, Unit PriceReturned Quantity, Return Date
Region, Customer ID, Sales ChannelReturn Reason, Refund Amount

Check the grain of each table. One order can contain several products, and a product line may be returned in more than one event. If you join tables without understanding this relationship, you may multiply order quantities and overstate returns.

2. Clean and validate records in Excel

Before analysis, create a working copy and standardise the fields. Useful checks include:

  • Remove exact duplicate return records using a stable Return ID.
  • Trim extra spaces and standardise category and reason labels.
  • Check blank Order IDs, Product IDs, dates and returned quantities.
  • Flag returned quantities that are zero, negative or greater than the purchased quantity.
  • Confirm that every return record matches a valid order line.
  • Check that refund amounts are numeric and consistent with the business rules.

For a simple row-level validation, use Excel formulas such as:

=IF(OR([@[Returned Quantity]]<=0,[@[Returned Quantity]]>[@[Ordered Quantity]]),"Review","Valid")
=TRIM(CLEAN([@[Return Reason]]))

Do not automatically delete unusual records. A return quantity greater than the order quantity may be an error, but it could also reveal a split-order or data-model issue. Flag it, investigate it and document the resolution.

3. Calculate meaningful return metrics

A return count alone can be misleading. A product with 50 returns from 10,000 units sold may be healthier than one with 12 returns from 40 units sold. Use a denominator that matches the business question.

Unit return rate = Total returned units ÷ Total units sold × 100
Order return rate = Orders with at least one return ÷ Total eligible orders × 100

Keep unit return rate and order return rate separate. They answer different questions. Also define the eligible sales period and allow enough time for customers to return recent purchases; otherwise, the newest orders may appear artificially healthy.

4. Use SQL to find products and categories that need attention

After validating the data, use SQL to aggregate sold and returned quantities at the product level. The following example assumes each table has one row per product order line and that return rows are already deduplicated.

WITH sales AS (
    SELECT
        product_id,
        product_name,
        category,
        SUM(quantity) AS units_sold
    FROM order_lines
    WHERE order_status = 'Completed'
    GROUP BY product_id, product_name, category
),
returns AS (
    SELECT
        product_id,
        SUM(returned_quantity) AS units_returned
    FROM return_lines
    GROUP BY product_id
)
SELECT
    s.product_id,
    s.product_name,
    s.category,
    s.units_sold,
    COALESCE(r.units_returned, 0) AS units_returned,
    ROUND(
        100.0 * COALESCE(r.units_returned, 0)
        / NULLIF(s.units_sold, 0), 2
    ) AS unit_return_rate_pct
FROM sales s
LEFT JOIN returns r
    ON s.product_id = r.product_id
ORDER BY unit_return_rate_pct DESC;

For a fair comparison, filter both datasets to the same sales cohort and return window. In a production model, also join on the appropriate order-line key—not just Product ID—when returns need to be matched to individual purchases.

5. Investigate return reasons, customer segments and categories

Once high-return products are identified, look for patterns rather than assuming the product itself is always the problem. Break the results down by:

  • Return reason: damaged, wrong item, size or fit, not as described, changed mind.
  • Product category: compare categories using rates as well as counts.
  • Supplier or brand: check whether issues cluster around a particular source.
  • Region and fulfilment centre: look for shipping or handling patterns.
  • Sales channel and customer segment: compare like-for-like groups without treating correlation as proof of cause.

For example, a high “not as described” rate may justify reviewing product images and descriptions. A concentration of “damaged” returns from one fulfilment centre may warrant a packaging or handling audit. These are hypotheses to validate with operational evidence—not conclusions to make from a chart alone.

6. Build a Power BI product returns dashboard

Bring the cleaned order and return tables into Power BI, establish the correct relationships, and create measures for units sold, units returned, unit return rate, returned order count and refund value. Use a consistent date table so that users can compare periods accurately.

Add slicers for date, category, region, supplier and channel. Show both the return rate and the number of units sold so viewers do not mistake a tiny sample for a major business issue. Include definitions in a tooltip or information panel.

7. Turn findings into practical business actions

A useful analysis ends with actions that can be tested and measured. Match each validated pattern to a responsible team and a follow-up metric.

  • Product information: improve size guides, specifications, photos or compatibility details when “not as described” is a leading reason.
  • Quality control: review supplier batches and inspection records when defects cluster around particular products.
  • Packaging and delivery: test stronger packaging or handling changes when damage-related returns are concentrated in a route or warehouse.
  • Customer experience: clarify product selection guidance when customers repeatedly choose the wrong variant.
  • Monitoring: track return rates by product cohort after each change and compare with a suitable baseline.
Analyst’s takeaway: Prioritise products with a high return rate, enough sales volume to make the signal meaningful, and a reason pattern that the business can investigate. A ranked list without context is not yet a recommendation.

8. What should you include in a portfolio case study?

To make this project useful in a portfolio, document the original business question, data dictionary, cleaning decisions, validation checks, SQL queries, metric definitions, dashboard screenshots and recommendations. Explain one finding clearly and show how you would measure whether the proposed action worked.
